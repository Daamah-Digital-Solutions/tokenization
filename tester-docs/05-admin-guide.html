Admin Guide

The admin guide covers Django Admin operations: reviewing KYC, approving properties, moderating marketplace activity, managing operator groups, watching transactions, and handling support actions like refunds, payouts, and account changes.

Time: ~60 minutes
Prereqs: Tester Onboarding
Test account: admin@capimax.com (superuser)

1. Accessing Django Admin

  1. Open {backend_url}/admin/ directly in your browser

    Local: http://localhost:8500/admin/

  2. Log in with admin@capimax.com / TestPass123!

  3. You land on the Django Admin home page

Two admin surfaces

Capimax has two distinct admin areas. The Django Admin at /admin/ is the operational source of truth used in this testing round. There's a separate "Admin Dashboard" surfaced in the SPA — that's intentionally lightweight in this build. For real moderation work, use Django Admin.

3. Operator groups & staff accounts

Five pre-built groups let you grant scoped admin access to staff without making them superusers. Use these for any new operator account.

3.1 Create a new operator

  1. Accounts → Users → Add user

  2. Email, password, first/last name

  3. Set is_staff = True

    Important: do NOT set is_superuser = True unless you really mean it. Staff + group permissions is the right combination.

  4. Save. The user can now log into /admin/ but sees nothing yet.

  5. Edit the user → scroll to Groups → add the appropriate operator group

  6. Save. The user can now see and modify the records that group is allowed to touch.

Privilege escalation check

Log out, log back in as the new operator, and try to access an area they shouldn't have. e.g. a KYC Reviewer trying /admin/marketplace/marketlisting/ should see "You don't have permission to view or edit anything." If they CAN access it, the group has too many permissions — file a bug.

4. KYC review queue

  1. KYC → KYC profiles

  2. Filter by status = pending

  3. Open a pending profile

    You see:

    • User identity (name, email, DOB, nationality)
    • Submitted documents (passport image, selfie)
    • Compliance checks (sanctions screening, PEP)
    • Notes & audit log

  4. Review the document image (click to enlarge)

  5. Make a decision:

    • Approve — flip status to approved. Investor can now invest.
    • Reject — status to rejected; require a reason in the notes
    • Require additional documents — status stays pending, send back to investor with a comment

  6. Save. The investor receives a notification.

4.1 Bulk approve

  1. From the list view, check the checkbox next to multiple pending profiles

  2. In the "Action" dropdown, choose Approve selected

  3. Click "Go". Each one flips to approved.

Audit trail

Every approval/rejection is logged in KycAuditLog with timestamp, reviewer (you), and a snapshot of the prior state. Review the log to confirm your action was recorded.

5. Property approval

  1. Properties → Property approvals

  2. Filter by status = pending or submitted

  3. Open a pending approval

    You see the property's headline fields, all uploaded documents, the owner's previous track record, and any comments.

  4. Review the property detail:

    • Does the title/description match the documents?
    • Are the financial fields internally consistent (total_value = token_price × total_tokens)?
    • For Ready: does monthly_rental_income look plausible vs total_value?
    • For Under-Construction: is expected_completion_date in the future?
    • Are required SPV fields filled?

  5. Choose an action via the dropdown:

    • Approve selected properties — flips Property.status to approved. Owner can now tokenize.
    • Reject selected properties — status to rejected; require notes
    • Mark selected as under review — intermediate state pending more info

  6. Save

6. Watching tokenizations

After approval, the owner triggers tokenization. As an admin you should watch this happen so you can intervene on failures.

  1. Blockchain → Smart contracts

  2. Filter by network = BNB Smart Chain Testnet

  3. You see all deployed contracts:

    • Templates (RealEstateToken, RentalIncomeDistributor, PropertyContractFactory) — no property reference
    • Per-property clones — one row per tokenized property

  4. Click a clone to see its details: address, deployment tx, constructor args, status

  5. Blockchain → Token transactions shows every on-chain action:

    • Mint (investment-driven)
    • Transfer (marketplace trades)
    • processInstallment (graduated release)
    • distributeRentalIncome

6.1 Deployment failure recovery

  1. If a property is stuck in approved with no smart-contract row, the deployment failed

  2. Check the platform logs (in dev: backend console)

  3. If the gas was the issue, top up the platform treasury wallet on BSC Testnet faucet

  4. Ask the owner to retry tokenization from their dashboard. The flow is idempotent.

7. Investments & mint status

  1. Investments → Investments

  2. Filter by status. The key states:

    pendingCreated; payment not yet captured
    processingPayment in flight
    payment_confirmedCharge succeeded; awaiting mint dispatch
    pending_mintMint scheduled
    mintingMint in flight on chain
    completedTokens minted, investor sees them in portfolio
    mint_failedMint failed after retries; refund pipeline triggered
    failedOther terminal failure
    refundedAutomatic or manual refund issued
    cancelledInvestor cancelled before payment captured

  3. Open any investment to see the audit trail (status changes, timestamps, related payment, related tx hash)

7.1 Manual mint retry

  1. Find a stuck investment in mint_failed

  2. Confirm mint_retry_count < 3

  3. Use the "Retry mint" action from the dropdown

    Behind the scenes this calls retry_failed_mint which resets the retry counter and re-dispatches.

7.2 Trigger an installment manually (for testing)

In the test environment installments don't run on schedule. To test the flow, manually fire the next installment.

  1. Investments → Installment payments

  2. Pick the next unpaid installment for the test investor

  3. Use the "Process selected" action

    Charges the saved card, calls processInstallment on chain. The investor's token balance grows.

8. Marketplace moderation

8.1 Listings

  1. Marketplace → Market listings

  2. Filter by status: active, partially_filled, filled, cancelled, expired

  3. Operator actions on a listing:

    • Cancel selected listings — force cancel (use for suspicious activity)
    • Mark selected as expired — for listings past their expiry that didn't auto-expire

8.2 Trade orders

  1. Marketplace → Trade orders

  2. Operator action: Cancel selected orders

8.3 Trade transactions

  1. Marketplace → Trade transactions

  2. Stuck transactions (in_escrow longer than 24h) should be reviewed

  3. Operator action: Mark selected as FAILED — only use after confirming on-chain state matches

8.4 Escrow resolution

  1. Marketplace → Escrow accounts

  2. Filter by status = holding

  3. For each row, two operator actions:

    • Force release — buyer receives tokens, seller receives funds
    • Force refund — buyer gets refund

Use force-release/refund with care

These actions bypass the matching engine's normal completion path. Use only when the engine has clearly failed (e.g. an escrow stuck for > 24 hours with no chain activity). Always document the reason in the audit log.

9. Payouts & refunds

9.1 Withdrawal approvals

  1. Payments → Wallet withdrawals

  2. Filter by status = pending

  3. Review each request:

    • User's wallet balance covers the amount
    • User has completed KYC
    • No suspicious patterns (e.g. immediate large withdrawal after large deposit)

  4. Approve via the action menu, OR reject with notes

9.2 Refunds

Most refunds are triggered automatically by terminal mint failures. The admin's job is to verify they happened correctly. Manual refunds are also possible from the Refunds page.

  1. Payments → Refunds

  2. Filter by status = pending (manual refunds requiring approval)

  3. For credit-card refunds, the refund processes through Stripe automatically once approved.

  4. For bank/crypto/wallet refunds, status stays in pending until operationally processed off-platform.

9.3 Manual refund creation

  1. Find the payment in Payments → Payments

  2. Click Issue refund (link on the payment detail)

  3. Set amount (full or partial), reason

  4. Submit. A Refund record is created and processed.

9.4 Broker commission payouts

  1. Broker → Broker commissions or Payouts (depending on schema)

  2. Approve pending payout requests

  3. Mark as paid once funds have actually left the platform

10. Broker applications

  1. Broker → Broker applications

  2. Filter by status = under_review

  3. Open an application. Review:

    • Business name + license number
    • Compliance attestation checkboxes
    • Supporting documents
    • Country — is the platform licensed to operate there?

  4. Approve / reject. On approve, a BrokerProfile is auto-created and a referral code is assigned.

11. Audit trail

Capimax logs every admin action. The audit trail is useful when you're debugging "who changed what".

  • KYC → KYC audit log — per-profile audit of reviewer decisions
  • AdminPanel → Admin actions — cross-app admin action log
  • Blockchain → Contract events — per-contract event log decoded from chain
  • Each model also has Django's built-in "History" link in the top-right of the detail page

12. Emergency procedures

12.1 Pause the marketplace

If you spot exploit-like trading activity, you can globally pause new listings:

  1. Blockchain → Smart contracts → pick the PropertyContractFactory

  2. Call emergencyPause (action available to factory admins)

    This stops all new on-chain activity from the factory.

  3. Investigate, then call liftGlobalPause when safe

12.2 Disable a property

  1. Properties → pick the property → set status to suspended

  2. Investors can no longer invest until status flips back

12.3 Ban a user

  1. Accounts → Users → pick the user

  2. Set is_active = False

  3. Save. The user can no longer log in. Their active investments are preserved.

Log in as a non-staff user at /admin/"Please enter the correct email address and password" — even if the credentials are correct. Non-staff users must not get any admin context.
